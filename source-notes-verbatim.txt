Part 1 — Diffusion Models

At Stability we have a tool called Brand Studio. It's meant to help brands generate images for marketing. Brand Studio puts a big text box in front of people and asks them to type in a description of the image that they want generated 

[ image ]

The problem is that people have become so trained in the last two years by ChatGPT and Claude, etc., that when they see a big text box they assume that they're going to be able to chat. If you go through the logs, a significant number of our prompts to get through the system are from people having a 1-way conversation with a robot that can’t really understand what they’re trying to stay.

Diffusion image generation models like Stable Diffusion are trained by replacing random pixels in an image with static noise 

[show picture, maybe animated ]

 and associating the description of that image with those pixels in such a way that starting with just noise and a description, the model is able to guess which pixels are missing and from that generate an image of just about anything 

[ weird ai slop picture ]


The standard example of diffusion with text, to make it even clearer, is going through a book and crossing out  words and characters and then having someone try to read it

The more the more descriptive your prompt, the more likely you are to generate a high-quality image.

Contraat:

If someone prompts for “a cat” or “a shoe”, likely to get something very generic 

[ show picture ]

Likewise diffusion models can get confused with attempts at dialogue and will often try to represent instructions or questions as parts of the image

[ show bad example ]

So what do we do about it? Well, Google solved this problem by creating a hybrid model with nano banana, that can understand chat prompts and reason about the image before building it in a series of steps, using a combination of both auto-regressive (standard LLM) and diffusion-based approaches to image generation (along with a few other tricks)

But we weren’t Google and at that point didn’t even have very many ML researchers at the company, so our very AI-pilled product manager Max come up with a fantastically complicated plan for solving this problem, mostly on the frontend.

This is the story of building a better UI for diffusion image generation and it’s about to get very technical very fast  🚀

Cloudflare Basics

I feel like, to explain how the agents SDK and workflows works, I need to explain two other related cloudflare technologies.

So everyone knows, basically, that Cloudflare is a CDN, a massively distributed edge network.

One of the first core features that Cloudflare added was called Workers, which are very similar to AWS lambdas, except they run at the edge, so they're extremely low latency , and they're built using something called V8 isolates instead of containers so there are almost no cold start costs. Almost everything that Cloudflare has built is built since then is built on top of Workers. Workers can also communicate with one another.

The mental model for workers is:

here is spin up some temporary compute resources as close to the request  as possible 

[ picture maybe? ]

On top of workers, Cloudflare built durable objects which builds on workers by giving each instance a unique name, a local database and a “hibernating” WebSocket connection.

Now the mental model changes. where Workers were a sort of a generic serverless compute platform,) taking on requests and spinning up as needed ), with durable objects every user or org  can now have their own dedicated stateful computing instance. 

It's the smallest cutest little cloud computer to ever exist and when you’re not using it it goes to sleep but because it’s durable if you ever wake it up it still has all your data intact. Pretty cool 😎 

At some point they realised this is basically the perfect primitive to build an AI agent framework on top of. 

Durable objects or durable agents??


Cloudflare Agents SDK

What the Cloudflare Agents SDK adds is a dead simple way to keep state in sync between the browser and the agent.  

The agent has a setState function, backed by SQL and when that’s called on either the server or the frontend, the other is notified immediately over the WebSocket.

State sync solved. 

Setting up the connection between the client and server is just a couple lines of code, there’s a custom hook that lets you do this in react.

Making server functions available for clients to call is available by adding a simple decorator to any of your backend methods 

This is really the first problem we are trying to solve: client and server communication. And it's almost all comes for free.

Agents don’t have to make all the decisions

One thing that I think might bother people about this talk is that many people assume that agents have to be smart or in charge for them to really count as agents. 
 
And really what we’re talking about there is Deterministic vs Probabilistic Workflows

Does it not count as an agentic workflow if we're telling it which Models to call and in which order? 

Does the agent have to be the one making the decisions about what to do next, which tools to call, and what arguments to send? 

My hot take is that we should rely on deterministic workflows as much as possible. 

Why? They're essentially cheaper because you don't need an agent to decide every turn and they're easier to test and eval because you know all the possible outcomes in advance. It’s also how you can encode human taste and decision making into an agentic process. Which I think  is a good thing. 

We don't need to cede all control to the robots just yet
